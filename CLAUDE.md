# Project notes for the agent

- Product rules every view follows (Drew's, settled 2026-10-12):
  - One floor: a streak counts when it leads its field (rank 1, ties included), meaning the longest active or the all-time longest. There's no score floor past the miner's keep floor, and that applies to team pages, streaks broken, the schedule's digests and counts, game pages and Top Streak-Breakers alike. A long list pages with "see more"; it isn't cut. Don't add a score cutoff, a cap or an "of note" filter to a list without asking.
  - Numbers nest: when two views show related counts, one must be explainable from the other. For example, a game's "N broken" holds every break the streak-breakers page credits the winner for that game (`breakers.test` pins it). Before changing either side of a mismatch, explain why it's there.
  - Ranks, not scores: the crown score orders lists but is never shown. A ranking shows a place, like SKR (Streak King Rank, with an ⓘ), not points; readers take a method on trust when they can eyeball the result.
  - Words: a team that ended a streak by winning *broke* it and is a *breaker*, never "stopped"/"stopper".
  - One list rule (settled 2026-10-15, `specs/streak-list-rule.spec.md`): every list of streaks on the site is `src/lib/list.ts` over the mine, filtered to the view's slice. The mine keeps each run under two definitions at most, the one with the fewest conditions and the one the team places highest under; a *placing* is the run under one of them (its conditions, the team's place in that field, the rates). The rule's verbs are the repo's: **admit** (which runs are on any list: a place within `LIST.admit.rank` under either placing, or the all-time longest), **pick** (which definition a run is shown under: the fewest-conditions placing that admits it), **order** (the score) and **group** (sub-streaks under their run). A view filters and may weight (at-risk by the chance the game ends the run, breakers by points); it never admits, re-words or re-includes. The mine is weight-free and every file carries the rule's inputs, not a score, so the page scores and a knob never re-mines. The knobs are `LIST`; `?tune=1` on any list opens the tuner (`Tuner.jsx`, on the dev server only: `readTuneOn` is false in a production build, since a shared `?tune=1` link reached readers), with "why" under every row; `list.golden.test.ts` pins the orderings that matter and that every view nests.
  - Simple and trivia (settled 2026-10-25, `specs/trivia.spec.md`): a streak is *simple* when its definition has at most two conditions, a margin outcome (`dir=W10`) counting as one, and no trivia chip (`trivia.ts`: full moon, weekday, weekend, team color, vs a first-year coach, state, after a win, the halftime score, the clock; after a bye, month, mascot and the game-shape chips are not trivia). Every list is simple: `listCrowns`, `listRuns` and `listBroken` take a `part` (`'simple'` by default, `'trivia'`, `'any'`), judged on the definition the row is shown under. Trivia is a button under each of the team page's All-time and Active sections (it opens that section's trivia streaks in place), one folded "and N trivia streaks" line under the digests, a game page's lists and a team page's breaks, a word in the board's sentence, share text and card from a third condition (the add menu says so), and off the breakers board entirely (no points, not counted, not listed). The knobs are `LIST.admit.maxConditions` and `admit.triviaChips`. The trivia chips are `trivia.ts`'s list, not `list.ts`'s trivia tier: the tiers are prices the miner's keep floor reads (`crowns.ts`), so moving a chip between tiers re-mines. Short or empty lists are the rule working: it's better to show nothing than something that isn't interesting, so don't add a fallback that fills a list back up.
- This is a Vite + React static site deployed to GitHub Pages by `.github/workflows/deploy.yml` on every push to `main`. It serves at `https://<domain>/<repo-name>/`.
- `package.json` "name" must equal the GitHub repo name. `vite.config.js` derives the `base` path from it.
- `site.config.js` holds the domain, title, description, and OG copy. `scripts/prerender.mjs` reads it at build time and writes the meta tags, JSON-LD, sitemap, and the index-site embed script tags into `dist/index.html`, plus one prerendered page per current FBS team at `dist/team/<id>/index.html` with its own OG image.
- `npm run build` is `vite build` plus the prerender, which also mines every team's streaks and writes `dist/crowns/<id>.json` (a team page embeds its active list) and the schedule's digests to `dist/games/digests.json` (the games pages embed it); the dev server serves both from `dist/` when a build has run (`serveBuilt` in `vite.config.js`, which also serves the prerender's static pages, `/blog/`, a post, the feed and `/data/`, and the built `assets/` they link, so they render in dev) and mines in the page otherwise, which takes minutes. The prerender fills `dist/index.html` in place, so rerunning it alone fails ("could not find an empty #root"): run `vite build` before it. The deployed HTML contains the rendered page, so `src/main.jsx` uses `hydrateRoot`, and nothing may read `window` during render. Apply URL state in a `useEffect` after mount. The only path-derived state is the team page (`/team/<id>/`), passed in as `initial.page`.
- `/games/` (the calendar button on the board) is the schedule: one week of one season at a time, a year picker (every season since 1936) and a week picker (each option with the week's dates) in the title; the schedule section's filter box narrows the week to games with a team whose name contains what was typed (page state only). Only simple runs the list rule admits as the week began (a place within the admit knob, or the all-time longest) show anywhere on the schedule, with no score floor, the trivia ones folded into one line under each digest: a game's "N broken" counts every streak it ended, both sides and covering runs, so it always holds what the streak-breakers page credits for that game (`breakers.test` and `list.golden.test` pin it). The digests' files carry rows, not a split or a score: `brokenDigest` and `atRiskWeek` make the digest in the page from the knobs in force. Every list of broken runs (the week digest, a breaker's page, a team page's breaks) is `BrokenRow.jsx`. Above a completed week's games sits its broken-streaks digest (`broken.ts`: the runs a result that week ended; a row's small print leads with "now the all-time longest streak", a link to the definition's all-time board with no team open, else "was the longest active streak", then since when, then the result without its date), above the running week's its at-risk streaks (`atRisk.ts`: every longest active streak its games put on the line, ranked by the crown score times the chance the game ends it, from the line under a normal margin model (σ 13.5), no floor; a game without a line stays out, and a covering streak is a coin flip). A played week is a results ledger, the games that broke the most streaks first with no day dividers (score, the count broken, the game's top broken run beneath), a scheduled week the schedule by day (kickoff, the line as of the build, how many streaks it puts on the line, the one most on the line beneath; `topOnLine` in `team.ts`); a row opens the game's page. The running season's digests come from the build's `dist/games/digests.json` (`digests.ts`); a past season's week digest is built from its season file (below). `/games/week/<n>/` is a running-season week's address, `/games/<season>/week/<n>/` a past season's, `/games/at-risk/` the running week's at-risk streaks, each running-season one prerendered with its own head. Both digests show 6 rows, one per team, the rest behind "more", and each heading carries a small link button that moves the URL to the section and shares it. Their OG images are the share worker's (`share/og.png?broken=<n>` and `?risk=<n>`), drawn from the rows the prerender writes to `dist/share/weekly.json`, so a new week has a card the moment the site deploys; `gen:og -- --weeks` still writes `public/og/week/` but nothing links to it.
- A game's page is `/game/<date>/<away>-at-<home>/` (`-vs-` for a neutral site; `game.ts` keys, paths and lookups). Played: the streaks it ended whose team led the field as the week began (rank 1, ties included; one as long as the longest run ever under its definition is labeled "now the all-time longest streak", from the miner's `everLen`/`everN` on every broken run), and the definitions under which a team became the sole leader because of it; unplayed: every streak either side puts on the line, by what the game can take away. The rows come from the season files, `dist/games/<season>.json` (`seasonFile.ts` the format, `seasons.ts` the build's rows from the miner): the running season from the full four-chip space, older seasons from definitions of up to two chips (`HIST_CHIPS` in `crowns.ts`). The build prerenders every running-season game (about 900 pages, each embedding its own rows), every past season's weeks, and `dist/404.html`, the app shell; an older game has no file, so GitHub Pages answers with the shell and the app boots on the address, and the share worker turns that into a 200 with the game's own head, JSON-LD and card (`share/og.png?game=<key>`); a never-major opponent's name comes from `meta.others`. The old matchup address (`/team/<id>/?vs=<opp>|next`) opens the game's page.
- `/breakers/` (the trophy button on the board) is Top Streak-Breakers: every team by the streaks it ended by beating their owner this season (`breakers.ts`: a winning run of any margin ended by a loss to the breaker; a covering run ended by a miss only under `BREAK.covers`, off). "Break" and "breaker" are the words, in the UI and the code (the page was Streak-Stoppers for a day; `/stoppers/` still parses). Only simple runs count (trivia is off the board: `listBreaks` reads the simple part, and the worker's past-season branch skips trivia rows), and only two kinds, worth `BREAK.points`: the all-time longest under its definition, 10, and the one that led the active field as the week began, 4; divided by one plus `BREAK.discount` per condition; one row per run (the sub-streaks are in the file, flagged subStreak, and don't count). The page never shows points, only the order they make, SKR (Streak King Rank, with an ⓘ); the leaderboard is one dense row per team (logo, SKR, streaks broken with the all-time and longest-active counts beneath, a pill per team whose streaks it broke, the biggest break), sortable by team, SKR or streaks broken. A season's breaks come from its season-file rows (`breakersFromSeason`), the same rows the schedule and the game pages read, so a game's count holds every break credited for it. The build writes the running season's to `dist/breakers/<season>.json` (the full four-chip space) and prerenders the page with it embedded; `/breakers/<id>/` is one team's broken streaks (whose they were, a logo and count each, a tap filters; the rows read like the schedule's), prerendered per breaker with a slice of its rows; a leaderboard row opens it. A year picker in the title opens a past season, `/breakers/<season>/` and `/breakers/<season>/<id>/`, worked out in the browser from `dist/games/<season>.json`: definitions of up to two conditions (`HIST_CHIPS`), which the page says, so a past season's numbers don't compare with the running season's. Those addresses aren't prerendered: the share worker answers them with the shell and their own head and card, scoring the season file with `breakScore.ts` (pure, shared with `breakers.ts`; `rankOrder` breaks a points tie the same way on both sides). A breaker can be any team, below FBS or since departed (its address parses from the payload's ids, and it has no team-page link). A team page embeds its own slice and shows the first six under "Streaks broken this season" with its SKR and a link to the full list. The share worker draws the cards (`share/og.png?breakers=<season>` and `?breaker=<id>`) from rows the prerender adds to `dist/share/weekly.json`.
- The by-opponent board, "as [team]" (`src/lib/asTeam.ts`, `asBoard` in `createModel.ts`): the board with one FBS team fixed and its opponents as the columns, each column the team's run under the definition against that opponent, which is the team's own row on the board for that definition plus `vsteam:<opponent>` (the same run and words; `asTeam.test` pins the nesting both ways). `as` is a view axis, not a chip: rows keep `ti` as the run's owner and carry `vs`, the opponent; the open column is the opponent (`?t=`, FBS or not); "vs [team]" and `as` never meet (the reducer drops one for the other); the by-opponent board's default definition is no conditions, so `?as=<id>` says its chips outright; the star is off on it (it saves a definition). Two of its definitions are pages, the questions people ask about a team: `/team/<id>/losing-streaks-by-opponent/` ("Who has beaten Auburn the most times in a row?", every opponent's longest winning streak over it) and `/team/<id>/win-streaks-by-opponent/` ("Who has Auburn beaten the most times in a row?"), prerendered per team with the question as the h1, the answer as a lead sentence (`asLead`), an ItemList and a line each in `llms.txt`; a team page's "Streaks by opponent" section is the winning list, what the team is good at (the top five, one row per opponent, with the series now), with the losing page a link under it. Any other state is the root with `?as=<id>`. The worker words `?as=` boards and a column open on a page, and draws the card (`share/og.png?as=<id>&dir=L`) from `asBoard` with the team's mark beside the heading. Ranks-not-scores for free: the list is one team's runs by length, nothing is scored, and nothing from the mine is read.
- Three things open, one view each: a streak opens the board's panel (`?t=<id>`: the streak and its ledger; on desktop one card in the grid's row with the column, the panel to its right, ← → moving it to the previous or next column and Escape closing it; on a phone a vaul bottom sheet over the board with the open column lit and centered in the rail, two snap heights, closed by a drag, the ×, Escape or Back), a game opens its page (`/game/<date>/<away>-at-<home>/`, in place of the board), a team opens its page (`/team/<id>/`, in place of the board; its name is a picker for any other team, and its streaks live there). An old `/team/<id>/` link that carries a definition still opens the panel; an old matchup link (`?vs=`) opens the game's page.
- A new view (the schedule, the breakers, a game page) follows two conventions. First, anything that reads a point in time is addressable by season and week, the way the schedule is (`/games/`, `/games/<season>/`, `/games/<season>/week/<n>/`): parse it in `url.ts` (`<x>FromPath`, `parseUrl`, `toUrl`, a `<x>Url()` helper), add its action and resets to `view.ts`, seed it from the path in `main.jsx`, and prerender each running-season address with its own title and description (the breakers page has season addresses, though only the running season is prerendered; the share worker words the rest). Second, every shareable address gets its own treatment in the share worker: a card at `share/og.png?<kind>=…` (`workers/share/index.ts`), drawn from rows the prerender writes to `dist/share/weekly.json` or from the model, the page's `og:image` pointing at it, and `CARD_VERSION` bumped whenever what a card draws changes; a section inside a page that is worth sharing gets a link button that moves the URL to its address (`linkSection` in `App.jsx`). The data a page embeds goes under its own `initial` key (`crowns`, `digests`, `seasonRows`, `breaks`), never a view key's name, and the prerender renders from the decoded file it embeds so the hydrate matches; a hook seeds from `initial` and fetches only when a page needs what the slice lacks. Add the address to the sitemap, a `url.test`/`view.test` case, and an `App.test` hydration of the prerendered shape.
- Search (`specs/seo.spec.md`): every page the prerender writes is in `dist/sitemap.xml`, and the index site's `sitemap-index.xml`, the one registered in Search Console and Bing, lists that sitemap through the `sitemapUrl` field on this project's card there (a postbuild step in the index repo appends it). Three kinds of page exist for search. (1) The named definition pages, `src/lib/landing.ts`: a curated table of definitions, each at its own path (`/longest-home-win-streaks/`, `/longest-losing-streaks-in-college-football-history/`), prerendered as the board on that definition with an h1 and title worded the way people search; the path is the definition's canonical address, so `toUrl` writes it whenever the board is on that definition (`?t=` rides along), `parseUrl` reads the definition from it, and the worker words a panel open on one from the table (`shareText`). The default definition is the root and must not be a landing (`landing.test`). `Landings.jsx` lists every one under the grid as real links. (2) The weekly posts: markdown under `content/posts/` (`content/posts/README.md` has the frontmatter), read by `scripts/lib/posts.mjs` into static pages at `/blog/<slug>/` (the site's styles, no app script, Article JSON-LD), the index at `/blog/` and RSS at `/blog/feed.xml`; Drew writes them (Thursday the at-stake streaks, Sunday the broken ones), and pushing the file publishes it. `deploy.yml` also builds Thursday 13:00 UTC so the at-risk page is that morning's lines. (3) Every past season's weeks, `/games/<season>/` and `/games/<season>/week/<n>/`, prerendered from the season file with the week's broken digest in the head (about 1,650 pages); the worker's past-season branch is now a fallback. Game pages carry SportsEvent JSON-LD, team pages SportsTeam, leaderboards an ItemList. For chat apps and other text readers: each board column's words are `.sr-only` text inside its buttons (`columnWords` in `Grid.jsx`; the logos are `aria-hidden`), the prerender writes `dist/llms.txt` (every definition page with its lead sentence), and the deploy's `indexnow` job pings IndexNow (Bing, which ChatGPT search, Copilot and DuckDuckGo read) with `scripts/indexnow.mjs`: the board and definition pages on a push, the whole sitemap on the scheduled refresh; the key is the `public/<key>.txt` file, public by design. Cloudflare's Crawler Hints is on too. A placeholder team id carries a colon (`x:sacramentostate`), and the game-path regexes allow it.
- Shareable state goes in the URL, one write per change: `src/lib/url.ts` parses and builds it (pure, tested), `writeUrl` in `src/urlState.js` writes it. A definition change is a `replaceState`; opening a panel or a game, or moving between the board and a page, is a `pushState` that records the URL underneath, so the close button steps back when Back would land on the same thing (`close()` in `App.jsx`). Params `c` (chips), `dir=L|U|C|N` or `dir=W10|L7` (won or lost by at least that margin, every game; `src/lib/outcome.ts` reads it, and the miners, the team page and the broken digest walk the one mined margin, 10), `scope=active` (default is all-time), `week=1`, `run`, `t`, and `vs` (the old matchup address, read only). The view's state and its rules (a new definition resets the column limit, all-time drops the week filter) are the reducer in `src/lib/view.ts`. The analytics embed counts each write as a pageview.
- Code layout: `src/lib` is TypeScript (`npm run typecheck`); components are still JSX. `createModel(payload)` in `createModel.ts` decodes a payload into per-team game rows and evaluates definitions; `model.ts` builds the app's one model from `src/data/payload.json`. The chip catalog is `chips.ts` and reads only row fields; `minedChips.ts` is the list the miner walks: the plain chips plus one derived chip per choice of color, mascot, team, conference, month, state, and leading/trailing at half (443 chips, keys in URL form like `vsteam:alabama`). One rule for every streak list: `crowns.ts` mines every team's run under every definition of up to four mined chips, in one pruned depth-first walk (a prefix under the floors is dropped with its whole subtree), for four readings at once (active, all-time, the runs every game ended, and every week's new sole leader), each run with its rank, field and the longest other run. The walk is `mineCore.js`, plain JavaScript with no imports, so it runs on worker threads: one per core at the build (`mineWorker.js`, pieces of the walk dealt on demand) and on Web Workers in the dev server; about 50s on a 10-core laptop; `list.ts` is the list rule (above): at page time it admits, tells, scores (bits past chance at a rate mixing the field's and the team's own, plus the lead over the field and a rarity bonus, less each chip's tier cost, the log of its choices (a rival's opponent chip priced as one of the team's rivals), a margin cost and a sparsity cost for a definition that keeps few of the team's games, weights in `LIST`) and groups them; it cuts nothing a list shows (the miner's `KEEP_FLOOR` is the only floor, and a crowns file keeps every run placed `FILE_RANK` or better under either placing so the admit knob has them to reach). `team.ts` is what a team page and a game page read: season record, next game, and the team's streaks from its crowns file with the next game that qualifies. One rule for every list of a team's streaks (the list rule): a run counts when its place under either placing is within `LIST.admit.rank` (1: the longest active, or under all-time the longest ever; 3 is the medal rule), with no score floor past the miner's own keep floor. `mineCrowns` returns the file's raw rows (no cutoff, no cap; up to ~1,800 a team), so a team's crowns files are every run it is placed `FILE_RANK` or better in, unscored, in two files (`crowns/<id>.json` the active runs, `crowns/<id>.all.json` the all-time ones; `crownsPath`), plus the all-time top (`crowns/<id>.top.json`) a team page embeds; a team page embeds its active file and its all-time top (`crowns/<id>.top.json`, `topRuns` in `list.ts`: the runs behind the All-time section's first five, with the count of all-time trivia streaks), so each section's default rows are in the prerender. From the top it is the header and next game, Streaks by opponent, All-time, Active, Streaks broken this season, then the schedule. All-time and Active each show five simple rows and nothing past them, plus a trivia button, and the all-time file loads only when the All-time trivia button opens; a game page fetches each side's active file only. The team page, the broken and at-risk digests, the on-the-line counts and the game page all read the same lists, and every long list pages with "see more" (`Tellings`/`MoreButton`, `PAGE` rows at a time). The board's team panel is the streak and its ledger only; a team's streaks are on its page. `schema.ts` holds the payload's sentinels and flag bits, and the build scripts import it directly (Node strips the types). The conference chips (`confgame`, `nonconf`) can't read a game of a team that was independent that season (`known`, off `ownConf` on the row), so an independent has no conference or non-conference streaks. Tests are Vitest (`npm test`), next to the code; the mining tests share one mine, about 4 minutes on a laptop. With `STREAK_MINED=data/build/mined.json` the tests read the raw mine the last `npm run build` wrote to that file instead of mining (stamped with the payload's build time, the chip list and the keep floor; a stale stamp warns and mines), and CI sets it so the build's mine feeds the tests.
- Analytics: `track()` in `src/lib/analytics.ts` wraps `window.dhAnalytics?.track(name, props)`, optional-chained because the embed is third-party and blockable. Events: definition (fires on every board load, including hydration, so its unique count is board loaders, not definition changes), team open, team page, game (`from`), games (`from` when a page's icon bar opens it), games year, broken week, breakers (`from`: board, team page, breaker), show more (the board's columns), share, save/unsave/apply saved streak, lead apply (a streak opened from a list; `from` says which, e.g. `broken all-time` for a digest's all-time link), team trivia (`scope`: `active` or `all`, a team page section's trivia button opened), week filter, kofi (`from`: notes, footer, or `icons <page>`), blog (`from`: the page whose icon bar it was). Every URL write is a pageview, so a visitor who changes the definition gets a pageview with a query string. Drew's own devices and the exclusion filter for them are in the Mixpanel scorecard board (memory: `mixpanel-scorecard`).
- Citing (`specs/reach.spec.md`): every address is a permalink, and the `/data/` page and the notes ask writers to name the site and link it. The cite and embed buttons (`Cite.jsx`) came out 2026-10-18: in three weeks only Drew had clicked them. `/data/` is a static page the prerender writes (Dataset JSON-LD, CC BY 4.0 for the computed files, the sources' own terms for the results) listing every JSON file the build writes; it's in the sitemap and linked under the board's streak boards. The share worker sends two more server-side to the same project (the token is the embed's public one): `share unfurl` when a crawler fetches a board or matchup URL the worker rewords (`agent`: slack, discord, imessage, twitter, …, never the raw user agent or an IP; `country`; the URL's `chips`, `dir`, `scope`, `team`, `vs`) and `share card` for every og.png request (`cached`). A browser's visit is the embed's to count, so the worker reports crawlers only.
- The icon bar (`NavIcons` in `Dateline.jsx`) is the same on every page: find a team, the schedule, the streak-breakers, the star (the board only, since it saves a definition), the blog, ko-fi and share, less the icon for the page it's on.
- A scheduled game is one no build has recorded a result for. It stays a team's next game past its date until the weekly rebuild writes the outcome (the payload is built once a week in season, so a Saturday game is unknown until then, not gone). A scheduled game's line (`upcoming.sp`, from the same CFBD `/lines` call as the season's closing lines) is the line as of the build. It is shown on the next-game row, the team page and the matchup; no chip reads it, because it moves until kickoff.
- Hover interactions use `onPointer*` events, not `onMouse*`, so they work on touch. Every select is `Picker.jsx`, a Radix dropdown dressed like the definition sentence's words; no native `<select>`.
- Team marks are committed under `public/logos/` (one-color, result squares) and `public/logos-color/` (column heads, next-game chips, the ledger), one pair per ESPN id, fetched by `scripts/gen-logos.mjs`. `build-current.mjs` nulls the ESPN id of a team whose marks aren't committed (the chip shows its initial) and lists it in `data/build/logo-wants.json`; run `gen-logos`, then `build-current` again, when it reports new opponents. Color marks use ESPN's dark-background variant when it measurably reads better on the page (rule and the by-eye exceptions are in `gen-logos.mjs`); delete a file to refetch it.
- Favicon and OG images are generated by `npm run gen:favicon` (which copies drewhoover.com's own set from the index repo, `~/Projects/DrewHoo.github.io/public`, the same mark every sibling site ships) and `npm run gen:og` on a developer machine and committed. CI does not regenerate them. `gen:og` writes `public/og.png` and `public/card.png` (laid out on a 1200-wide canvas and rasterized at 96 dpi, so the files are 1600×840 and 1600×1000, the sizes the prerender declares; the worker's cards are 1200×630), 136 team cards under `public/og/team/`, and one card per completed week under `public/og/week/` (that week's broken streaks), drawing from the payload, so re-run it after a redesign, after any grid rule change (it mirrors the column layout, including the reserved top slot on a live run), after a change to what a team leads (a team card's "king of N" counts read the crowns rule), and whenever a fresher board is worth committing; `STREAK_MINED=data/build/mined.json` skips the mine. `npm run gen:og -- --weeks` renders just the week cards, which nothing links to any more (a week's page uses the worker's `?broken=` card), so there's no need to run it weekly. Text is drawn as opentype.js glyph outlines: sharp's librsvg ignores `FONTCONFIG_FILE`, and opentype.js 2.x emits NaN path data, so it is pinned to 1.3.4.
- Social previews: drewhoover.com's DNS is on Cloudflare (origin stays GitHub Pages, SSL Full (strict)), and the share worker (`workers/share/`, name `streak-king-share`) sits on `drewhoover.com/cfb-streak-king/*`. It rewrites `<head>` for definition boards and matchups — words from `src/lib/shareWords.ts` (pure; its tests pin it to definition.ts) plus `dist/share/meta.json` — and draws each definition's board as a PNG at `/cfb-streak-king/share/og.png?c=…` (workers-og; fonts committed beside the worker, the serif a static instance because satori can't parse variable fonts; data from `dist/share/payload.json`, raw-GitHub fallback). Origin data fetches are edge-cached with a UTC-date cache key so a pre-deploy 404 dies the same day. The `worker` job in `deploy.yml` deploys it after every push to main (not the weekly refresh) with the `CLOUDFLARE_API_TOKEN` repo secret; by hand, `npm run worker:deploy` (wrangler is OAuth-logged-in on the dev machine; it's a pinned devDependency, and `deploy.yml`'s `wranglerVersion` is the same version). `npm run typecheck` covers the worker too (`tsconfig.worker.json`: the Workers runtime types in place of lib.dom, `env.d.ts` for the `.ttf` imports). The card's edge cache is keyed by `CARD_VERSION` in `index.ts`: bump it with any change to what a card draws. Every card with rows says how many there are in all and how many the rows leave out ("760 streaks broken", "+754 more broken"), from totals the prerender writes beside the rows. To see a card before deploying, run the worker locally against the build: `vite preview` on 4173, then `npm run worker:dev`, which passes `ORIGIN=http://localhost:4173` (the worker reads `env.ORIGIN`, the live site by default) and `NO_REPORT=1` (`report()` returns early, so no test request reaches the analytics project); the deploy sets neither. The worker holds `weekly.json` in memory for the UTC day, so restart it after a new prerender. Anything the worker can't word passes through untouched, so the site never depends on it.
- Dev server: `npm run dev`. If port 5173 is busy, `npm run dev -- --port 5174`.
- Worktrees: `data/raw/` and `data/build/` live only in the main checkout. Symlink both into the worktree to run the pipeline, and never `git add -A` there, because the symlinks are not covered by the `.gitignore` directory patterns.
- The window starts at `FIRST_SEASON` in `scripts/lib/window.mjs` (1936). Before 1978 Howell's pages are the only game source; `fbs-span-bridges.json` and `extra-games.json` hold the researched wartime seasons, each row with a source and quote.
- `data/ref/unplayed-postseasons.json` rules on team-seasons that ended without a postseason game and why (a declined bid, a school's no-bowl policy, a conference rule, a ban), each row with receipts (url + verbatim quote). `src/lib/unplayed.ts` joins the rows to the winning runs that lived through them, in two classes: the team's own call (`chose`) and a rule it was under (`ruled`); a streak's panel notes it under the ledger, and the Method notes say so in one line. `node scripts/data/check-receipts.mjs data/ref/unplayed-postseasons.json` string-matches every quote against its page (cached under `data/build/receipt-pages/`); run it after editing the file. Two `played` rows record bowl games the payload's postseason flag missed (Maryland's 1977 Hall of Fame Classic, Florida's 2006 title game); `build-payload.mjs` now flags those, and every January game, so they clear on the next rebuild.
- Data rulings live in `data/ref/` and are applied at build time with fail-loud checks: `repole-errata.json` (parse-repole fails on an entry that matches no row), `coach-overrides.json` (`team|season` → `{ segments, receipts, note? }`; build-payload must report 0 unresolved coach seasons), `alt-home.json`. Every researched row carries `receipts: [{ url, quote, note?, retrieved? }]` (or `[{ sources: [...] }]` for an entry that is a vote across named datasets, like the errata) — the receipts-research skill's receipt object. `npm run check:receipts` string-matches every quote against the page text saved under `data/research/pages/` (committed; CI runs it offline, so a new receipt needs its page saved first: run `node scripts/data/check-receipts.mjs data/ref` without `--offline`). `npm run coverage` (after build-payload) reports receipt coverage per ruling file, unmatched names, the build's numbers against their floors, and the open rows of `data/research/triage.json` (source disputes) and `leads.json` (things a research pass raised outside its brief). The "vs [mascots]" and "vs [color] schools" chips read `team-traits.json`, generated by `scripts/data/gen-team-traits.mjs` from CFBD's team list ruled by `mascot-classes.json` (every nickname's name-group and classes; a name-group ships only with 2+ current-FBS teams, so there is no "vs Horned Frogs") and `color-overrides.json` (one identity color per school where the hex-hue rule gets it wrong: Auburn is orange, Purdue is gold). Re-run the generator after editing a ruling; build-current attaches the traits, so CI needs no extra call. After changing the errata, run `scripts/data/export-errata.mjs` against a checkout of `DrewHoo/repole-errata` and push it; that repo is the public CC0 copy.
- The `dataviz-pages-site` skill covers everything else: build-time data, researched datasets, mobile, dates, SEO, registering the project card on the index site.
